# v1.2.0 · 提醒功能失效排查、系统日历同步与时间基准修正

> 本文回答三个问题：
> 1. 已经授予通知权限，为什么一条提醒都收不到？改了哪些地方？
> 2. 让待办直接写进系统日历，可行吗？怎么做？
> 3. App 到底能不能拿到设备的当前日期时间？怎么保证大模型算对提醒时间？

对应代码版本：`versionCode 5` / `versionName 1.2.0`
验证环境：Android 14 模拟器（1080×2340@420dpi），应用 targetSdk 34

---

## 一、结论先行

**「已授权但没有任何通知」不是权限问题，是三重叠加的功能性缺陷。**

| # | 根因 | 位置 | 后果 | 严重度 |
|---|---|---|---|---|
| 1 | 息屏被当成「不该打扰」，直接 `BLOCKED` | `IdleDetector.assess()` | 手机放桌上/口袋里全是息屏，待办到点 100% 不发 | 致命 |
| 2 | 亮屏时长永远取不到，评分永远达不到阈值 | `IdleDetector` + `Settings.lastScreenOnAt` | 就算亮着屏，最高只能拿 60 分（阈值 70），判不到「空闲」 | 致命 |
| 3 | 没有到点闹钟，只有一条被反复重置的周期闹钟 | `AlarmScheduler` / `Application.onCreate` | 每开一次 App 就把 15 分钟周期闹钟重新计时，等于永不触发 | 致命 |
| 4 | 通知渠道是 `IMPORTANCE_LOW` | `Notifier.ensureChannels()` | 不进状态栏、不弹横幅，用户主观上「什么都没有」 | 高 |
| 5 | 发不出去时静默 `return`，不留痕 | `Notifier.showSoftReminder()` | 排查时无从下手 | 中 |

一句话：**权限一直是对的，是「什么时候该发」的判定逻辑把所有场景都判成了不该发。**

## 二、逐条定位过程与证据

### 2.1 根因 1：息屏即拦截

改造前 `IdleDetector.assess()` 的第一段是一票否决：

```kotlin
if (!power.isInteractive) {
    return IdleAssessment(IdleState.BLOCKED, 0, listOf("息屏"))
}
```

`ReminderEngine.run()` 拿到 `BLOCKED` 就直接 `Outcome.Skipped(...)`，不写日志、不重试。

真实使用场景是「15:00 提醒我打电话」，15:00 时手机在口袋里 —— 息屏。于是这条提醒直接被丢弃，且不会补发。

### 2.2 根因 2：评分永远差 10 分

改造前的评分表（满分 90）：

| 项 | 满分 | 依赖 |
|---|---|---|
| 亮屏时长 | 30 | `settings.lastScreenOnAt` |
| 无操作时长 | 35 | UsageStats / 广播 |
| 前台应用类别 | 20 | UsageStats |
| 充电 | 5 | 电池广播 |

`lastScreenOnAt` 只在 `ScreenStateReceiver` 收到 `ACTION_SCREEN_ON` 时写入。而 receiver 是在 `Application.onCreate()` 动态注册的 —— 冷启动时屏幕**已经是亮的**，那一次 `SCREEN_ON` 广播早就过去了。结果这个值长期是 `0`。

而代码里是：

```kotlin
val screenOnFor = if (settings.lastScreenOnAt > 0) now - settings.lastScreenOnAt else 0L
```

即**恒为 0，这一项恒得 0 分**。最高分 = 0 + 35 + 20 + 5 = 60 < 阈值 70。

同一段代码里「无操作时长」也有个副产品 bug：

```kotlin
val idleFor = maxOf(now - lastInteractionAt(), now - settings.lastInteractionAt)
```

两个值都是 `0` 时，`idleFor` 变成 `now - 0`，日志里出现过 `静置1793519160s`（约 56 年）。这个荒谬值反而白送了满分 35，掩盖了问题。

### 2.3 根因 3：周期闹钟被自己反复重置

```kotlin
// Application.onCreate()
AlarmScheduler.schedule(this)

// 内部
am.setInexactRepeating(
    AlarmManager.ELAPSED_REALTIME,
    SystemClock.elapsedRealtime() + ASSESS_INTERVAL_MS,
    ASSESS_INTERVAL_MS,
    pi
)
```

三个问题叠在一起：

1. **每次冷启动都重排**：同一个 `PendingIntent` 调 `setInexactRepeating` 会用「现在 + 15 分钟」重新计算首次触发。用户只要 15 分钟内打开过一次 App，这条闹钟永远响不了。
2. **`ELAPSED_REALTIME`（非 WAKEUP）**：设备深度睡眠时不唤醒，要等下一个自然唤醒点。
3. **Doze 压制**：非精确周期闹钟在 Doze 下被推迟到维护窗口，间隔会递增到数小时。

### 2.4 根因 4 / 5：通知渠道与静默失败

```kotlin
NotificationChannel(CH_SOFT, "柔性提醒", NotificationManager.IMPORTANCE_LOW)
```

`IMPORTANCE_LOW` = 无声音、无震动、**状态栏不出图标**、不弹横幅。就算发出去了，用户下拉通知栏才能看见。

```kotlin
if (!canPost()) return   // 布尔都不返回，也不写日志
```

权限被拒 / 渠道被关时完全静默。

## 三、修复方案

### 3.1 判定逻辑：从「拦不拦」改成「怎么提」

`IdleDetector` 重写，原则是：**柔性通知本身静默，息屏发出并不打扰，所以没有理由拦。**

保留的一票否决只剩四种真正不该出现的场景：

| 场景 | 处理 |
|---|---|
| 静默时段（默认 22:00–07:30） | BLOCKED，不补发 |
| 通话中 | BLOCKED |
| 系统免打扰开启 | BLOCKED |
| 正在打游戏/看视频（前台娱乐类且静置 < 90s） | BLOCKED |

息屏改为返回 `IDLE(score=100, reasons=["息屏","静默发送"])`。

拿不到信号的项一律给**中性分**，不再给 0 分：

```kotlin
score += when {
    screenOnFor < 0 -> 15          // 亮屏时长未知，中性
    screenOnFor > 10 * 60_000 -> 30
    ...
}

val lastTouch = listOf(lastInteractionAt(), settings.lastInteractionAt)
    .filter { it > 0 }.maxOrNull()
val idleFor = if (lastTouch == null) -1L else now - lastTouch
score += when { idleFor < 0 -> 15; ... }
```

阈值同步下调：`IDLE_SCORE_THRESHOLD` 70 → 60，`SEMI_IDLE` 40 → 35。

**更关键的一点：评分不再决定「发不发」，只决定「措辞」。**
`ReminderEngine.dispatchOne()` 只在 `state == BLOCKED` 时跳过；`ACTIVE / SEMI_IDLE / IDLE` 全部放行。评分 ≥70 时通知正文多一句「现在应该有空」。

### 3.2 排期：改成「每条待办一个精确闹钟」

`AlarmScheduler` 全部重写：

```kotlin
// 每条待办一个，requestCode 用 id 的哈希低 15 位
am.setExactAndAllowWhileIdle(AlarmManager.RTC_WAKEUP, dueAt, dueIntent(ctx, memo.id))

// 没有精确闹钟权限时降级（Doze 下仍会唤醒，误差几分钟）
am.setAndAllowWhileIdle(AlarmManager.RTC_WAKEUP, dueAt, pi)

// 兜底巡检：用 set 自续期，不用 setInexactRepeating
am.setExactAndAllowWhileIdle(RTC_WAKEUP, now + 15min, assessIntent)
```

三层保障：

1. **精确到点**：`RTC_WAKEUP + setExactAndAllowWhileIdle`，Doze 下也能唤醒；
2. **兜底巡检**：15 分钟一次，自续期（每次触发后重排下一次），不会因为冷启动被打断；
3. **事件对账**：亮屏、解锁、开机、改时间、换时区、跨天，六个时机都重排。

「稍后 10 分钟」也单独排了精确唤醒，不让承诺的 10 分钟变成 15–25 分钟：

```kotlin
app.repo.nextSnoozeWake(now)?.let { at ->
    setAlarm(ctx, am, at, assessIntent(ctx, 2), 2)
}
```

新增广播接收器：

| 接收器 | 监听 | 作用 |
|---|---|---|
| `BootReceiver` | `BOOT_COMPLETED` / `LOCKED_BOOT_COMPLETED` / `MY_PACKAGE_REPLACED` | 开机、更新后重建全部闹钟 |
| `TimeChangeReceiver` | `TIME_SET` / `TIMEZONE_CHANGED` / `DATE_CHANGED` | 时间跳变后对账，并作废失效的亮屏时刻 |
| `ReminderActionReceiver` | 通知按钮 | 「稍后 / 标记完成」不打开 App 就能处理 |
| `ScreenStateReceiver` | `SCREEN_ON` / `USER_PRESENT` | 记录亮屏时刻，顺带补发错过的提醒 |

### 3.3 并发去重

到点闹钟、兜底巡检、亮屏对账可能在同秒内触发同一条待办。读-改-写不是原子的，实测连发了两条一模一样的通知（`reminder_log` 里 `t1|SHOWN` 出现两次，相差 9 秒）。

修复：

```kotlin
private val gate = Any()

fun dispatchOne(...): Outcome = synchronized(gate) {
    ...
    if (memo.lastRemindAt != null && now - memo.lastRemindAt < AppConfig.REMIND_REPEAT_MS) {
        return Outcome.Skipped("刚提过")
    }
}
```

`REMIND_REPEAT_MS = 20 分钟`。同时 `sync()` 排补发闹钟时跳过「刚刚提过的」，否则每次冷启动都会重发一遍。

### 3.4 通知本身

```kotlin
// 渠道 id 换成 suiji_soft_v2 —— 重要性创建后不可修改，只能换 id 才生效
NotificationChannel("suiji_soft_v2", "待办提醒", IMPORTANCE_DEFAULT)
    .setSound(null, null).enableVibration(false)   // 仍然静默

// 通知带动作
.addAction(0, "稍后 10 分钟", snoozePi)
.addAction(0, "标记完成", donePi)
```

`post()` 返回布尔，失败写 `reminder_log.result = FAILED_NO_PERMISSION`，排查有据。

### 3.5 设置页把状态摊开

新增「提醒与通知」分组：

| 行 | 内容 |
|---|---|
| 通知权限 | 实时读系统状态，未授权时红字 + 可点击申请 / 跳系统设置 |
| 到点提醒 | 「试一下」，直接投一条测试通知验证整条链路 |
| 提醒开关 | 原「闲时柔性提醒」 |
| 静默时段 / 检测灵敏度 | 保留 |

启动时的权限弹窗改为**只弹一次**（`Settings.notifAsked`），之后靠设置页红字引导。反复弹窗只会让用户一直点拒绝。

`SuiSwitch` 的点击区从 48×28dp 放大到 56×40dp —— 实测原来很难点中，用户会以为「开关坏了」。

## 四、系统日历：可行性评估与实现

### 4.1 三种方案对比

| 方案 | 权限 | 提醒可靠性 | 用户可见/可改 | 局限 |
|---|---|---|---|---|
| **A. 直接写 `CalendarContract`**（已采用） | `READ_CALENDAR` + `WRITE_CALENDAR` | 高 —— 由系统日历守时，不受国产 ROM 杀后台/自启动限制 | 是，日历里能看能改能删 | 需要运行时权限；多日历账户要选 |
| B. `ACTION_INSERT` 拉起系统新建界面 | 无 | 高 | 是 | 每条都要用户手动确认一次 |
| C. 生成 `.ics` 文件再导入 | 无 | 高 | 是 | 要用户找文件、选导入，最麻烦 |

**选 A 的核心理由**：这个 App 的最大风险是「后台被杀 → 提醒不响」。写进系统日历等于把守时的责任交给系统日历，这是当前 Android 生态里最可靠的一条路。代价只是两个运行时权限，且做成默认关闭的开关。

B 保留为降级路径：没授权时 `CalendarBridge.insertIntent()` 仍能拉起新建界面。

### 4.2 实现

`data/CalendarBridge.kt`：

```kotlin
fun push(memo: Memo): Long?      // 有 calendarEventId 就 UPDATE，没有就 INSERT
fun remove(memo: Memo): Boolean
fun calendars(): List<CalInfo>   // 只列 ACCESS_LEVEL >= CONTRIBUTOR 的
fun insertIntent(memo: Memo): Intent?
```

关键细节：

1. **全天事件**：`DATE_ONLY` 精度必须用 UTC 零点换算（`CalendarContract` 的硬性要求），否则会偏一天。
2. **提醒**：同时写 `CalendarContract.Reminders`（`minutes = calendarLeadMinutes`，默认 5，`METHOD_ALERT`），否则事件在日历里没有提醒。
3. **幂等**：`memo.calendarEventId` 存事件 id，改时间后再推是 UPDATE 而不是重复插入。DB 从 v2 升到 v3 加了这一列。
4. **没有可写日历怎么办**：新装系统、没登录账号的机器上一个可写日历都没有。此时自动建一个 `ACCOUNT_TYPE_LOCAL` 的「随记」日历（必须带 `CALLER_IS_SYNCADAPTER` 参数，否则插入被拒）。
5. **开关语义**：默认关闭。打开时把已有的、带时间、还没写过的待办（最多 30 条）补写一遍；关闭时不删除已写入的事件（那是用户日历里的数据，删要用户自己决定）。

### 4.3 实测结果

在没有任何日历账户的模拟器上开启同步：

```

  cal_sync = true
  cal_id   = 1

  title=和张总过报价单,           dtstart=1793545200000, dtend=1793547000000, calendar_id=1
  title=给陈总回个电话,           dtstart=1793519360000, dtend=1793521160000, calendar_id=1
```

## 五、时间能力核查

### 5.1 结论：能拿到，而且一直是准的

App 一直在用 `System.currentTimeMillis()` + `ZoneId.systemDefault()`，与设备时间天然同步，无需任何权限。

时间解析（`TimeNormalizer`）也一直以设备本地时区为基准，「明天下午三点」算出来就是设备时区的次日 15:00。这一点没有 bug。

### 5.2 但有三个「同步保障」的缺口，都已补上

| 缺口 | 原来 | 现在 |
|---|---|---|
| 用户改了系统时间 / 换了时区 | 没人监听，已排的闹钟仍按旧基准触发 | `TimeChangeReceiver` 监听 `TIME_SET`/`TIMEZONE_CHANGED`/`DATE_CHANGED`，重排全部闹钟并作废失效的亮屏时刻 |
| 跨天 | 「今天/明天」的展示靠实时计算，但闹钟不重排 | `DATE_CHANGED` 也在监听列表里 |
| 传给大模型的时间基准不全 | 只给 `now = 2026-11-01T15:29`，却要模型返回**毫秒** | 改为给 `now_epoch_ms` / `now_local` / `timezone` / `weekday` / `today`，并要求模型只回本地时间字符串 |

### 5.3 一个真实的「算错 8 小时」隐患

原提示词：

```
now = 2026-11-01T15:29:35
dueAt 必须是与给定 now 同一时区换算后的毫秒时间戳
```

模型看到本地时间字符串，却被要求输出 epoch millis。它最容易的做法是按 UTC 反推，于是得到比正确值少 8 小时的毫秒。

而原来的校正逻辑容差是 24 小时：

```kotlin
if (isStrongRule(rawExpr) && diff > 24 * 3600_000L) 用本地值 else 用模型值
```

8 小时 < 24 小时 → 错误值被原样接受 → 提醒提前 8 小时，用户看到的现象还是「没提醒」。

两处修正：

1. **提示词只给本地时间，毫秒由本机换算**

```kotlin
fun promptBlock(ms: Long): String = buildString {
    append("now_epoch_ms = ").append(ms).append('\n')
    append("now_local = ").append(isoSeconds(ms)).append('\n')
    append("timezone = ").append(zone().id).append(" (UTC").append(utcOffset(ms)).append(")\n")
    append("weekday = ").append(weekdayCn(ms)).append('\n')
    append("today = ").append(localDate(ms))
}
```

Schema 从 `dueAt: 1730000000000` 改成 `dueLocal: "2026-11-02T15:00"`，并明确写：**不要计算毫秒时间戳，你算容易错 8 小时。**

解析侧优先 `SuiClock.fromLocalIso(dueLocal)`，没有才回落老的 `dueAt`。

2. **校正容差 24h → 2h，并识别时区错位特征**

```kotlin
val diff = abs(localValue - modelValue)
val looksLikeTzShift = diff >= 55 * 60_000L && diff % 3_600_000L < 5 * 60_000L
return when {
    isStrongRule(rawExpr) && (diff > 2 * 3600_000L || looksLikeTzShift) -> localValue to localPrecision
    diff > 12 * 3600_000L -> localValue to localPrecision
    else -> modelValue to modelPrecision
}
```

偏差接近整小时（1h / 7h / 8h）时直接判定为时区错位，用本地规则覆盖。

## 八、已知限制

1. **国产 ROM 的自启动限制**：部分 ROM 会阻止 `BOOT_COMPLETED` 广播，重启后闹钟可能丢失。缓解手段是系统日历同步 —— 那条路不受影响。这一点反而加强了「日历同步」的价值。
2. **精确闹钟权限**：Android 12+ 的 `SCHEDULE_EXACT_ALARM` 在部分 ROM 上默认关闭。代码已判断 `canScheduleExactAlarms()`，不可用时降级为 `setAndAllowWhileIdle`，误差在几分钟内。
3. **静默时段仍会丢弃**：22:00–07:30 到点的待办不会在深夜响，次日亮屏后由 `SCREEN_ON` 对账补发。这是设计选择，不是 bug。
4. **日历同步只处理「有时间的待办」**：无时间的待办（`dueAt == null`）不写日历，因为没有可放的时间点。
5. **`IMPORTANCE_DEFAULT` + 静默**：部分 ROM 会强行给默认级别加上横幅。若遇到，用户可在系统通知设置里把渠道调到「静默」。
