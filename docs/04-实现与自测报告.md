## 2. 与设计说明书的实现差异

设计文档写的是「最优解」，落地时在**不牺牲功能**的前提下做了减法，以降低 BUG 面、缩短首次可运行时间。差异如下，均不影响产品承诺。

| 设计文档 | 实际实现 | 原因 | 影响 |
|---|---|---|---|
| Room + KSP | `SQLiteOpenHelper` 手写 `memo` 单表 | 免去注解处理器与迁移样板，编译更快、崩溃面更小 | 无。字段与索引完全一致，后续换 Room 只需加 DAO 层 |
| Hilt 依赖注入 | `SuiJiApp` 持有容器，ViewModel 直接取 | Hilt 的 KSP + 插件链路在首次搭建时风险高 | 无。依赖方向仍是 ui → domain ← data |
| WorkManager 周期任务 | `AlarmManager.setInexactRepeating` 15 分钟 | 免一个依赖；柔性提醒对分钟级精度无需求 | 无。Doze 下同样会被批量唤醒 |
| OkHttp + kotlinx.serialization | `HttpURLConnection` + `org.json` | 零第三方依赖，APK 更小 | 无。OpenAI 兼容协议是标准 HTTP+JSON |
| Retrofit 风格 DTO | 手写 `JSONObject` 解析 | 同上 | 无 |
| `EncryptedSharedPreferences` | 自实现 `AndroidKeyStore` AES-256-GCM | 免 alpha 依赖，行为可控 | 无。密钥同样由 Keystore 托管 |
| 三张子表（memo/todo_meta/idea_meta） | 单表 + 可空列 | MVP 数据量小，单表读写更快更简单 | 无。`id` 主键已留好拆表余量 |

**同时保留的设计要点**：838dp 断点兜底、姿态优先判定、LLM 全链路降级、提醒三层节奏、通知 `IMPORTANCE_LOW` 静默、API Key 加密存储、连通测试 5 步体检、`configChanges` 防重建。

## 4. 自测记录

测试环境：Android 14（API 34）x86_64 模拟器，分辨率按 §4.5 切换；大模型用本地 mock 服务替代真实厂商。

### 4.1 冷启动与首屏

- 启动到首屏可交互约 700ms，无 ANR、无 FATAL。
- 空态文案、筛选胶囊、搜索框、录音 FAB 布局正常（截图 1）。

### 4.2 录入 → 入库

操作：点 FAB → 输入文字 → 点「收好」。

结果：卡片出现在「今天」分组下，类型标记为「待整理」并带 `?` 角标（无中文关键词时规则判 UNCLASSIFIED，符合设计）。数据库落库成功，列表刷新正常。

### 4.3 大模型配置与调用

用本地 mock 服务（`tools/mock_llm_server.py`，OpenAI 兼容）验证：

| 步骤 | 结果 |
|---|---|
| 配置校验 | ✓ 自定义（OpenAI 兼容）· mock-model |
| 网络连通 | ✓ 104ms |
| 鉴权验证 | ✓ 1204ms · 返回「在的」 |
| 分拣能力 | ✓ 识别为待办「和张总过报价单」，时间解析为 11月4日 |
| 结果保存 | ✓ 已记录，连接状态显示「✓ 正常 1204ms」 |

这证明：请求体构造、`Authorization: Bearer` 头、响应 `choices[0].message.content` 二次解析、JSON schema 校验、时间本地校正、错误分层，全部打通。

**无 Key 时的表现**：点「测试连接」第 1 步即失败，提示「API Key 无效或已失效 · 到设置页重新填写 Key」，后续步骤保持待执行，连接状态显示「✗ 配置不完整」。无崩溃、无弹窗拦截。

### 4.4 柔性提醒

构造条件：插入一条已到期的待办（dueAt = now − 1h），设备时钟设为白天（避开安静时段），灭屏再亮屏重置计时，然后静置 11 分钟不做任何操作。

实测结果：

- 设备 00:40（安静时段内）点击判定 → `得分 0 · BLOCKED / 安静时段`，**不提醒**。硬阻断生效。
- 切到白天、静置 703 秒后点击判定 → `得分 74 · IDLE`（亮屏 672s / 静置 703s / 前台 UNKNOWN），**当场派发**。
- `dumpsys notification` 抓到实际通知：

```
pkg=com.suiji.assistant id=1001 channel=suiji_soft
importance=2  vibrate=null  sound=null  defaults=0x0
category=reminder  vis=PRIVATE
android.title = 和张总过报价单
NotificationChannel{mId='suiji_soft', mName=柔性提醒, mImportance=2,
                    mSound=null, mVibrationEnabled=false, mShowBadge=false}
```

`importance=2` 即 `IMPORTANCE_LOW`，配合 `sound=null` / `vibrate=null` / `mVibrationEnabled=false`，物理上不可能响铃或震动，也不会产生 heads-up 弹窗——这正是「顶部淡色小字、绝不打扰」的实现依据。

调度、打分、频控、派发、静默通知全链路一次通过。

### 4.5 折叠屏适配

把模拟器改为 `2200 x 2480 @ 420dpi`（= 838dp 宽，与 vivo X Fold3 内屏一致）：

- 修复前：`838 < 840`，会错判为单栏——这就是设计文档 §3 指出的陷阱，实测复现。
- 修复后：`widthDp >= 720` 兜底生效，正确切换为「左 340dp 列表 + 分割线 + 右详情/空态」双栏，右栏空态显示「选一条看看，或者点右下角说一句」并带录音按钮（截图 2）。
- 改回 `1080 x 2340 @ 420dpi`（411dp）后自动回到单栏，无重启、无状态丢失。

### 4.6 空闲判定

设置页「查看当前空闲判定」实测返回：`得分 0 · BLOCKED / 安静时段`。

当时设备时钟为 00:40，落在默认安静时段 22:00–07:30 内，判定正确地一票否决。这条验证了三件事：安静时段计算正确、`IdleDetector` 的多路系统 API（UsageStats / AudioManager / PowerManager / NotificationManager）调用不崩溃、结果能被 UI 正确呈现。

## 5. 已知限制

1. **未在真机验证**：所有结论来自 API 34 模拟器。折叠屏的实际折痕区、悬停铰链坐标、OriginOS 后台策略需在 X Fold3 上复测。
2. **语音识别未实测**：模拟器无麦克风输入，`SpeechRecognizer` 只在点击时创建，未走到识别回调。真机需验证中文识别与 60s 分段续接。
3. **大模型用本地 mock 服务验证**：证明协议与链路正确，但未消耗真实厂商额度。用真 Key 时若有差异，只在提示词效果层面，不影响调用能否跑通。
4. **APK 使用 debug 证书签名**：可直接安装，但不适合上架应用商店。上架需生成正式 keystore 并配置 `signingConfigs`。
5. **未做混淆**：`isMinifyEnabled = false`，便于你测试时看堆栈。正式发布建议开启。
6. **分拣时间以模型返回为主**：本地强规则只在偏差超 24h 时才覆盖模型值（见设计文档 §7.6），这是刻意设计，避免模型已正确换算时被本地规则误改。

## 6. 如何换成你自己的 Key

APK 里**没有内置任何真实 Key**。交付构建的 `BuildConfig` 已清空（`LLM_API_KEY=""`），默认服务商为 DeepSeek、默认地址 `https://api.deepseek.com/v1`、默认模型 `deepseek-chat`，首次进入设置页显示「未配置 Key」。步骤：

1. 打开 App → 右上角「设置」
2. 「服务商」→ 选一个（DeepSeek / 智谱 / 通义 / Kimi / 火山 / 千帆 / MiniMax / 硅基流动 / OpenAI / 自定义），地址会自动填好
3. 「API Key」→ 粘贴 → 点「保存 Key」（Keystore 加密落盘）
4. 点「测试连接」→ 5 步全绿即可用
5. 之后正常说话录入

不配 Key 也能用，只是走本地规则分拣。
